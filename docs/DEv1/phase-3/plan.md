## Goal and non-goals

Materialize complete canonical `IntersectionObservation` V1 events from Bronze into topology-aware, nullable Silver facts with durable provenance, conflict invalidation, restartable persistence, bounded replay and an executable runtime acceptance. Preserve historical V2 SQL objects/data and current local changes; the Silver runtime itself is migrated in place.

Out of scope: implement Gold formulas/windows, Orion/NGSI, Projector, Spring/Dashboard, Phase 5 deployment, destructive conversion/deletion, Bronze semantic classification, Phase 2 certification, and any changes to the Master Plan. Silver never infers/repairs Bronze disposition.

## Runtime and migration decision (authoritative)

One official Silver V1 runtime is built by refactoring existing modules under `de/silver/` in place. The existing entrypoint remains `python -m de.silver.main` and the existing Compose service `de-silver-processor` is migrated; no `v1_main.py`, duplicate `v1_*` module set, second Silver service, or separate `de/silver_v1/` tree is planned. Add only capabilities with distinct ownership: `archive_resolver.py`, `lifecycle_refresher.py`, and `canonical_reader.py`; `source_binding.py` is optional only if independently useful. Audit imports and callers before removing V2-specific NGSI/Camera/RunStarted paths. V1 source allowlists reject V2 streams. Migration 008 adds V1 tables and does not mutate, rename, drop, truncate, or delete historical V2 tables/data. Phase 3 does not require the old Gold V2 runtime to operate against V1; it must not be started on V1 tables. Phase 4 supplies the V1 Gold adapter.

## Target architecture and contracts

```text
Bronze SQLite semantic authority (:ro) ── changes/high-water/current/invalidation/lineage
              │                                  │
              │ verified event point read        ├─ Silver SQLite: own cursor, frozen intents,
              ▼                                  │  event validity and replay state (:rw)
     Bronze ClickHouse observations (:read/reconcile) ──► V1 Silver processor
                                                         │ facts/dimensions/tombstone mirrors
                                                         ▼
                                              shared ClickHouse (migration 008)
                                                         │
                                   Gold-facing canonical Silver reader + validity overlay
```

Bronze SQLite is read-only and remains semantic authority. Silver uses its own SQLite WAL/FULL database, locks and checkpoints. SQLite source changes are authoritative; Bronze CH is a validated envelope/content mirror, not the incremental cursor. A new Silver namespace starts exclusive cursors at 0 and consumes the full retained `v1_changes` and `v1_invalidations` journals to fixed high-waters. No atomic bootstrap dependency. This relies on Bronze retaining complete history from sequence 1; verify the source binding and fail closed on a gap or changed authority. One additive Bronze method is needed: `read_valid_observation(namespace,event_id,expected_revision)`, returning the verified complete event only when current state is ACCEPTED at that revision and canonical CH content reconciliation succeeds. Use existing `current`, `read_page`, and separate `read_delivery_lineage` for state, journal and lineage. Do not reimplement Bronze classification or claim a frozen lineage snapshot from the event point read.

Journal-first bootstrap captures fixed change and invalidation high-waters, consumes from sequence 0 and records Silver-owned progress. For each ACCEPTED change, check current identity; a now-CONFLICTED event is suppressed. Appends above the captured high-water wait for the next pass. Restart recovers frozen intents and resumes after the last CAS cursor. Never initialize at “latest”. If authority is unavailable, no cursor advances; incomplete CH mirror retries.

Bronze duplicate deliveries are idempotent: same-content duplicate intents do not produce a new semantic change sequence. Each immutable fact freezes primary `first_raw_id` lineage and its transport/source-byte hashes. No initial/evolving-lineage snapshot is embedded in fact content. Complete current physical lineage is fetched separately through `read_delivery_lineage`. Conflicts invalidate every row for the event ID and include original/conflicting delivery IDs. Benign duplicates never rewrite facts or invalidate/rematerialize the logical event.

## Proposed additive V1 schema

Migration `de/migrations/008_create_silver_v1.sql` is next after existing 007. `IF NOT EXISTS`; no ALTER/DROP of 004 tables; include main and replay targets; migration runner must create every required table before worker starts. All ClickHouse objects use explicit column lists (no implicit defaults for domain values). Facts are append-only MergeTree and include `created_at` as processing metadata, but logical ordering is by event coordinates. Monthly partition by `toYYYYMM(created_at)` is operational only; no source-event semantics depend on processing month. ORDER BY starts with run/digest/event for fact locality. Bronze eventId is unique semantic identifier; CH may physically duplicate rows, so canonical reads reconcile and dedupe by identity plus full content.

## Archive resolver

Configuration `SILVER_V1_ARCHIVE_ROOT` points to producer artifacts root; immutable files are `<root>/runs/<simulationRunId>/run_manifest.json` and `network_topology_catalog.json`; lifecycle authority is `<root>/runs/active_run.sqlite3`; mount root read-only. Validate exact run identity through `manifest_identity()` (excludes only `runStatus` and `failedCycleCount`), generation, participants, configuration/profile/threshold/PCU/assets provenance and topology digest. Query the registry `runs` table read-only by previously known run IDs for `generation,run_id,manifest_identity,status,activated_at,updated_at`; do not instantiate `ActiveRunRegistry` (its constructor initializes schema) or use live-selection state for historical lookup. The producer has no bounded read-only lifecycle poll API; V1's resolver performs this read-only SQL query. When first resolving a run from an observation/archive, register it in a Silver SQLite known-run index. Poll this index in bounded batches at configurable interval (default 5 seconds; 1–300 seconds), including COMPLETE/INCOMPLETE/STOPPED runs; refresh after restart before lifecycle is reported current. Compare immutable `manifest_identity`/generation separately from registry status and manifest mirror. Registry status is authoritative; failed-cycle count and file hash come from the mutable manifest. On temporary status/count mismatch publish registry status, retain last confirmed count (NULL if never confirmed), mark `LAGGING` and retry. A registry identity/generation mismatch is an integrity failure. If registry is unavailable, preserve last-known projection but mark registry unavailable/freshness stale; do not infer status from manifest. Accept READY/RUNNING/COMPLETE/INCOMPLETE/STOPPED context. READY is pre-publication only: if the registry row is absent, Silver may cache READY context but must reject any observation as `RUN_NOT_PUBLISHED`; it must not materialize facts. A registry row with matching immutable identity and status RUNNING/COMPLETE/INCOMPLETE/STOPPED is required to materialize source events. COMPLETE observations remain valid; INCOMPLETE/STOPPED preserve individually valid events but set run-level partial status for Phase 4. Project every change in registry availability/version/status or manifest availability/mirror state/status/count/hash/freshness using the lifecycle semantic tuple defined above. Poll timestamps are SQLite operational metadata, not part of the tuple. Source does not retain all transitions, so no complete history is claimed. Catalog digest uses `contracts.topology.v1_digest.topology_digest`; resolve node via `node_to_tls` and approaches via `approach_edges`; require participant membership and exact event direction key set. Preserve exact metadata and file fingerprints. Never use active-run selection or current topology to interpret historical events. Cache immutable context by run/generation/digest/manifest_identity plus content hash. Replay uses historical archived context.

### Lifecycle projection update and recovery policy (R16)

Poll known run IDs every 1–300 seconds (default 5) in bounded batches. Mark lifecycle stale after three missed poll intervals (configurable threshold); a successful poll resets freshness. Registry status/version and mutable manifest state are observed independently. Registry status is authoritative; manifest status/count/hash are mirror evidence only. The lifecycle snapshot tuple is `(run_id,generation,manifest_identity,registry_state,registry_updated_at,run_status,manifest_mirror_state,manifest_run_status,failed_cycle_count,manifest_file_hash,lifecycle_freshness,failure_evidence_hash)`. Any tuple change is durably recorded and projected once, including SYNCED→LAGGING, SYNCED→UNAVAILABLE, and UNAVAILABLE→SYNCED. `observed_at` and poll timestamps do not independently trigger ClickHouse writes; persist `last_polled_at`, last-success times, last confirmed registry/manifest values and retry schedule in Silver SQLite. Freshness transitions (including CURRENT→STALE after three missed intervals and STALE→CURRENT on recovery) are part of the tuple and publish once. Identical polls write nothing. Registry outage retains the last known status/count/hash and sets registry and mirror unavailable plus freshness STALE, even if a manifest can still be read; it never infers status from that manifest. If no status was ever verified, status is NULL. When registry is available, manifest outage/lag retains last-confirmed count/hash, sets mirror state UNAVAILABLE/LAGGING, and never substitutes zero. Retry transient failures with bounded exponential backoff capped at 30 seconds, then return to configured polling. Restart restores known runs and cached values, polls before reporting lifecycle current. Immutable run dimension identity never changes. Gold can distinguish fresh and stale states; no complete lifecycle transition history is claimed.

## Availability and quality semantics

Registry resolution edge case: registry row absent plus manifest `READY` is pre-publication context only (`RUN_NOT_PUBLISHED` for any observation). If the row is absent while the manifest is RUNNING or terminal, fail closed as missing registry authority; never treat the mutable manifest as a lifecycle fallback.

| Source state | Silver representation | Coverage consequence for Phase 4 |
|---|---|---|
| Numeric including zero, with no availability entry | Numeric value preserved; status `MEASURED`/no unavailable entry | Counts as valid measured value |
| `null` + `UNAVAILABLE` | NULL plus exact availability code | Expected but not measured |
| `null` + `NOT_APPLICABLE` | NULL plus exact code | Excluded from applicable denominator, still explicitly classified |
| Optional field absent | NULL typed projection and absent key in canonical payload JSON; not a zero/default | No measurement claimed; Gold can distinguish absent from unavailable via JSON/presence metadata |
| Expected direction absent | Do not fabricate a direction fact; mark event/topology quality invalid and quarantine/block before any valid facts | Invalid topology, never complete denominator |
| Unexpected direction | Reject event facts as analytically valid; durable provenance error | Integrity failure; no widened topology |
| Partial intersection total | NULL and `PARTIAL_TOTAL` quality code when supported total cannot be verified; don't sum unknown/partial values into a complete total | Gold sees incomplete total |
| Optional top-level state absent | NULL plus absent key in payload JSON | Not zero/false/prior state |
| Scenario changes | Preserve each event's `scenarioId` on facts; run demand profile remains separate manifest metadata | Segment in Gold by event scenario as defined later |
| Direction metric availability differs | Independent nullable value/status per metric, never one aggregate direction flag | Per-metric coverage possible |

`quality_status`: `VALID` means topology/context verified and all present values satisfy shared contract; `VALID_WITH_UNAVAILABLE` means event is structurally/topologically valid but at least one required metric is explicitly unavailable or not applicable; `INVALID_TOPOLOGY` never enters canonical valid facts and is only a durable failure state. `quality_flags_json` stable codes include `METRIC_UNAVAILABLE:<name>`, `METRIC_NOT_APPLICABLE:<name>`, `OPTIONAL_ABSENT:<name>` only where useful, `PARTIAL_TOTAL`, and archive error codes on quarantine. Don't call a valid event invalid just because a metric is explicitly unavailable.

## Gold intersection total rule

Phase 3 may derive `total_vehicle_count` from directional counts because the verified topology supplies the exhaustive direction set. It is complete only if the event's direction keys exactly equal the archived approach set and every expected direction has a numeric `vehicle_count` without `UNAVAILABLE` or `NOT_APPLICABLE`. Then sum once across the declared direction set. If any count is absent, NULL, non-measured or direction coverage is wrong, emit NULL and `PARTIAL_OR_UNAVAILABLE`; do not expose a partial sum. This derived value and its rule version are part of Silver content hash/quality. Gold decides how it affects 60s/300s aggregation and coverage.

## Invalidation, persistence and checkpoints

SQLite schema (owned by Silver, additive) contains source binding and separate change/invalidation cursors with generation CAS; frozen event/output obligations and attempt/fault state; source high-water; event validity; lifecycle projection; local invalidation outbox; replay manifests. `BEGIN IMMEDIATE` protects state transition/obligation publication. A frozen obligation contains exact target, complete row content, expected content hash and source sequence. Order: capture fixed journal high-water; read page; verify current Bronze state and archive; freeze Silver intent; write dimensions/facts/tombstone; reconcile exact content; finalize validity and CAS. On conflict, atomically set local event state INVALIDATED and freeze outbox before advancing invalidation cursor. CH mirror retries independently. If crash occurs after local suppression but before CH write, canonical reads still exclude event and report backlog.

Cursor means “all Bronze journal entries through this exclusive sequence have durable Silver state and required output obligations”; it is not a Kafka offset or wall-clock watermark. Initial cursor is 0, proving full-history scan only under Bronze no-prune retention. CAS includes namespace, source binding, expected/next sequence and generation. Fixed high-water makes appends during processing wait for the next batch. Recover in-flight work first; never advance over a failed/unresolved entry. Before materialization, re-read current identity so an old ACCEPTED change that has since conflicted cannot be accepted.

### Bronze journal/source verification algorithm (P3-01)

`V1SemanticReader` in `de/bronze/checkpoint_store.py` is read-only (`mode=ro`, `PRAGMA query_only=ON`); the V1 tables are `v1_sequence`, `v1_changes`, `v1_invalidations`, and `v1_identity`. `v1_sequence.next_change` and `next_invalidation` are incremented inside the publication transaction, so allocated high-water is `next_* - 1`. The current SQLite code does not set `PRAGMA user_version` or `application_id`, and has no persisted database UUID. Bind checkpoints to canonical configured SQLite path, namespace, expected Bronze migration/schema constants (`MIGRATION_VERSION`, `BRONZE_SCHEMA_VERSION`), and a deterministic fingerprint of required `sqlite_master` table definitions/columns/keys. Never represent that composite as a cryptographic database identity.

At initial bootstrap, source replacement/path change, or schema-binding change, open read-only and execute `BEGIN`; all schema, allocator and journal checks below run in this one SQLite read snapshot. Require the source namespace to equal the configured Bronze V1 namespace (`live` in inspected `de/bronze/config.py`), the expected columns/keys, and exactly the supported V1 schema fingerprint. For each journal kind and namespace, read allocator `next_*` plus `COUNT(*)`, `MIN(sequence)`, and `MAX(sequence)`. Let `H = next_* - 1`. An empty journal is valid only when no rows exist and H=0 (no allocator row means H=0). A non-empty journal is complete from 1 only when `MIN=1`, `MAX=H`, and `COUNT=H`; primary key uniqueness then proves no missing sequence. If allocator is absent but rows exist, `next_* <= 0`, max disagrees with H, count differs from H, or min is not 1, classify as gap/pruned/corrupt and fail closed. Also verify every non-PENDING `v1_identity` with `change_sequence` joins to the matching `v1_changes` event/sequence/revision, and each invalidation has exactly one matching CONFLICTED change row via `invalidation_id`. This validates both journals; do not infer one from the other. Commit the read transaction only after all checks and bind the resulting source path/namespace/schema fingerprint plus verified starting boundaries.

The distinction among complete, empty, gap, pruned history, allocator inconsistency, wrong namespace/source, replaced path/database, unavailable source and corrupt schema must be explicit health/error outcomes. A path/schema/namespace mismatch or lower/reinitialized allocator than the last persisted binding means `SOURCE_BINDING_CHANGED`; sequence coverage failure means `CURSOR_GAP`; locked/unavailable SQLite means `AUTHORITY_UNAVAILABLE`; unknown schema means `SOURCE_SCHEMA_UNSUPPORTED`. A different database path is detected by path binding; a reset/replacement is detected when schema or allocator/history boundary differs. Since the source does not persist a UUID, an out-of-band replacement that reproduces the same path, schema, namespace and sequence contents is not distinguishable by SQLite evidence alone. Document this limitation and rely on the controlled read-only mount/source owner; do not claim protection against arbitrary out-of-band manipulation.

Run full coverage verification at initial bootstrap, worker restart before cursor resume, and whenever source path/namespace/schema binding changes. During normal polling, avoid rescanning all retained rows: verify the cheap schema/binding and allocator monotonicity, and validate each bounded page is contiguous from `after+1` through returned cursor; verify the allocator/high-water covers the page. If allocator regresses, a page has a gap, or boundary changes unexpectedly, stop and perform full verification/rebind only through explicit recovery. In an active append, hold the page's fixed high-water; later contiguous sequences are next-page work. Preserve the no-prune operational contract; do not create a snapshot API.

Replay is a deterministic rebuild of current effective Bronze state at a verified, stable source boundary, not arbitrary historical as-of reconstruction. The immutable replay manifest freezes source namespace and binding, change and invalidation high-waters, run ID/generation/topology digest/manifest identity, replay ID, reader/processor/schema versions, and archive content fingerprints. Before starting or resuming, compare Bronze's current sequence allocators/high-waters with the manifest. They must equal the frozen values and retained-history verification must still pass. During replay, recheck the boundary before each bounded batch and at completion. Because the allocators are monotonic and transition writes are transactional, any advance means the current source state may no longer match the frozen journal cutoff: abort with `SOURCE_BOUNDARY_CHANGED`, mark that replay ID non-resumable, and require a new manifest. Do not continue the old replay against changed `current()` state. Replay is therefore not allowed while Bronze is actively receiving changes; no historical snapshot subsystem is introduced. An unchanged source plus identical manifest/cursor supports deterministic restart/repeat; compare canonical logical row hashes excluding processing timestamps, and make a completed replay ID idempotent. Keep replay SQLite, checkpoints, IDs, locks and ClickHouse targets physically isolated; never mutate live state. An incomplete/aborted replay is not a successful reconstruction.

### Canonical Gold-facing Silver read protocol

Validity and completeness are separate. **Validity** means each returned event is currently Bronze ACCEPTED at its observed revision, Silver-local validity is VALID, and all required ClickHouse fact content is reconciled. **Completeness** means Silver's applied change cursor covers the page's captured Bronze change high-water and its applied invalidation cursor covers the captured invalidation high-water, under the verified namespace/source binding. Only complete reads are supported; the reader never returns a partial page as complete and Gold must not consume incomplete data as a finalized window.

**Integration method.** Implement `de.silver.canonical_reader.CanonicalSilverReader` as an in-process Python API; add no HTTP route/service. This matches the repository's Python readers and current `clickhouse_connect` pattern in `de/gold_runtime/silver_readers.py`. Return immutable `CanonicalPage`/`ObservationBundle` records and raise `CanonicalReadError` subclasses with stable `code` and `retryable` metadata. Reader issues SELECTs only. `CanonicalReadError` exposes only stable code/retryability; the plan's suggested HTTP mapping is applied by Phase 4, not stored as an HTTP status on the exception. A `CanonicalReadSession` owns a Bronze `V1SemanticReader` (`mode=ro`, `PRAGMA query_only=ON`), a Silver SQLite connection (`mode=ro`, `query_only`), and a ClickHouse client configured with SELECT-only credentials; it closes all connections and never shares Silver's writer connection/lock. Phase 4's Gold Python adapter maps typed errors at its later HTTP/API boundary. Phase 3 exposes no reader endpoint and does not mix status codes into Python return values.

**Query and pagination unit/order.** `CanonicalReadQuery` fixes namespace `live`, run ID, topology digest, and a finite half-open simulation-time range `[start_seconds,end_seconds)`; the same fields are bound in every token. One item is a complete event bundle: one intersection fact plus exactly one traffic and one signal fact for each archived direction. Query identity fixes `(namespace,simulation_run_id,topology_digest,[start_seconds,end_seconds))`; order is stable `event_id ASC`, with full exclusive key `(simulation_run_id,topology_digest,event_id)`. Never rely on ClickHouse physical order, offset, or processing timestamps. `limit` is 1–100 bundles (not fact rows/directions); never split directions across pages. Fetch all fact families for candidate event IDs, sort directional rows by `source_direction`, and verify exact cardinality against archived directions. Collapse identical physical duplicates by `(event_id,fact_family,direction,canonical_content_hash)`. Same logical key with differing hash raises non-retryable `CanonicalContentConflict` (`CANONICAL_CONTENT_CONFLICT`, suggested HTTP 500) and returns no page; missing rows/unknown validity raises `ValidityUnknownError`.

**Reader API and token.** `read_valid_page(query,after_key,limit,token=None) -> CanonicalPage(bundles,next_key,token,complete=True,has_more)`. `CanonicalReadQuery` is `(namespace,run_id,topology_digest,start_simulation_time,end_simulation_time)` with a finite half-open time interval. Candidate event keys come from the read-only Silver SQLite durable VALID index, filtered by query and ordered by the exclusive logical key; ClickHouse only supplies/reconciles fact content. Fetch `limit+1` keys to set `has_more`; final page has `has_more=false`. Each response token carries the next exclusive `after_key`, and a request must echo the token/key pair exactly. A consuming window scan stages bounded aggregate state and emits nothing until all pages use the same token boundary and `has_more=false`. On stale token it discards all staged aggregate state before bounded restart. Capture both Bronze allocator high-waters and binding at page start; require Silver applied change/invalidation cursors to cover them, verify current Bronze identity ACCEPTED at the same revision, local VALID state and reconciled CH content, then re-read both high-waters/binding at page end. Lag returns no rows and typed `SourceLagError` (`SOURCE_LAG`, suggested HTTP 503) or `InvalidationLagError` (`INVALIDATION_LAG`, 503). Authority failure is `AUTHORITY_UNAVAILABLE` (503); unknown validity/reconciliation is `VALIDITY_UNKNOWN` (503); stale boundary/token is `SNAPSHOT_STALE` (409); changed source binding is `SOURCE_BINDING_CHANGED` (409).

`CanonicalReadToken` binds version, full query/filter including finite time range, namespace/run/digest, source binding, both Bronze high-waters, both Silver applied boundaries, schema/reader versions, page size, ordering-key version and exclusive last key. It also binds cursor position to the echoed key so callers cannot skip/repeat keys by changing the cursor independently. Later pages require identical filter/page-size/version claims and unchanged source binding/high-waters. Any change during a page returns no rows; reusing a token after either authority advances is rejected. Error metadata is a Python contract, not an HTTP response; Phase 4 maps the stated suggested statuses.

**Progress/retry.** Validity (each bundle is currently accepted and reconciled) differs from completeness (both Silver cursors cover both captured Bronze boundaries); page consistency requires start/end boundary agreement; a multi-page scan is not a distributed snapshot. A stale token invalidates that page and the consuming scan discards its staged aggregate state, restarting at the first key with a fresh token. Retry same-page transient I/O at most three retries (four total attempts) with 100/250/500 ms backoff and the same token. Restart a stale full scan at most three times (four total attempts) with the same bounded backoff; exhaustion raises `SourceChurnError` (`SOURCE_CHURN`, suggested HTTP 503), reports incomplete and publishes no finalized result. A quiescent/stable source plus caught-up Silver permits completion. Do not promise starvation-free scans, cross-page atomicity, or historical as-of state. A conflict after the final check is later authority state handled by invalidation and a future scan.
