## Authoritative architecture and call flow

The Master Plan Phase 3 section (§335 onward) fixes V1 Silver as direct observation mapping from Bronze V1 plus the archived run topology. Its grains are one direction fact per declared direction and one intersection fact per observation, with run/topology provenance, lineage, nullable measurements, availability and quality. No Orion/NGSI reconstruction is in this path.

Actual current V2 execution path:

1. `de/silver/main.py:main` loads `SilverSettings`, validates live/replay namespace guards, acquires the SQLite/OS `InstanceLock`, constructs `SilverProcessor`, binds the health API, and starts it.
2. `SilverProcessor.start` opens `SilverCheckpointStore`, connects `BronzeReader` and `SilverClickHouseRepository`, verifies source and destination schemas, discovers source streams, runs recovery, marks READY, then starts the worker thread.
3. `BronzeReader.discover_streams` scans only `bronze_run_events` and `bronze_entity_events` for the configured topic allowlist. It does not read the V1 Bronze journal.
4. `process_stream_once` creates a checkpoint per namespace/source-table/topic/partition; initializes from ClickHouse `min(offset)`; reads offsets greater than the checkpoint; estimates lag from ClickHouse max offset; and checks ClickHouse processing ledger state by source event ID.
5. Non-idempotent records go through `TransformationEngine.transform`: JSON parse → V2 type classification → NGSI-LD property/relationship unwrapping → normalization → validators → one fact plus dimensions or quarantine.
6. The processor reconciles/inserts fact rows, then dimensions or quarantine, then writes the processing ledger, and advances the SQLite checkpoint using CAS after terminal records. The worker recovers partial writes through reconciliation of those ClickHouse targets.
7. `SilverClickHouseRepository` allowlists V2 tables and reconciles facts by V2 event ID, payload hash and business key. Replay routes to V2 `_replay` targets and suppresses selected dimensions. Health is a cached snapshot of ClickHouse, SQLite, schema, lock, lag and worker state.

The processor's current ledger id is `BronzeEntityInputRecord.event_id` for entity records, but a run record uses `bronze_canonical_hash`; this is not V1 `eventId` semantics. The checkpoint describes an offset in a ClickHouse table stream, not a Bronze semantic change sequence.

## V2 source dependencies and incompatibilities

The existing source schema is `de/migrations/004_create_silver.sql`, which creates historical V2 tables, including `silver_fact_camera_observation`, `silver_fact_run_event`, `silver_dim_scenario`, and `_replay` copies. Do not alter these tables in place. The fact builder defaults missing `waitingVehicleCount` and `arrivalRatePcuPerSec` to zero; signal timing defaults missing `timingMode` to `FIXED_TIME`; intersection flags default missing values to false; V2 numeric fields are often non-nullable. Those behaviors contradict V1 availability/absence semantics. V2 cardinality is entity-oriented, accepts separate Camera/RunStarted inputs, and depends on four canonical direction names. V1 has a complete event payload, permits topology-defined direction sets, and has no Camera or lifecycle event as a Silver input.

V1 also distinguishes the source `payloadHash` from the Bronze canonical observation hash. Both plus the physical delivery hashes and IDs must be retained. V2's business key lacks `topologyDigest` and V1 `eventId`, so existing key and duplicate logic cannot be reused as-is.

## Bronze-to-Silver contract verification

Bronze authority is `de/artifacts/bronze_v1/checkpoint.sqlite3` (replay has its own path); downstream opens it read-only with `V1SemanticReader`, `mode=ro`, `PRAGMA query_only=ON`. Available methods in the Phase 2 handover/source are `current(namespace,event_id)`, `read_page(namespace, kind='changes'|'invalidations', after, limit, high_water)`, `read_delivery_lineage(namespace,event_id,after_raw_id,limit)` and `read_invalidation_provenance(namespace,invalidation_id)`. `read_page` is exclusive cursor pagination with a captured high-water; each call takes its own page snapshot. Preserve that same high-water over the full scan. The current reader does not provide a direct API to fetch the canonical observation envelope by event ID from SQLite; `BronzeClickHouseRepository.read_valid_observations` is a paginated current-state scan, and is not an as-of API or point lookup.

Bronze ClickHouse `read_valid_observations` verifies `v1_identity.state='ACCEPTED'`, semantic revision, envelope validity, canonical content hash and content-reconciled observation plus required delivery lineage. It excludes current `CONFLICTED` identities. A page is current state, not historical time travel. Silver must use the journal for incremental work and use CH only as an output-content mirror. Silver must not repeat Bronze classification.

Design implications: bootstrap captures `current(namespace,event_id)`/change max sequence in a consistent SQLite read transaction (or a new API that returns state plus high-water atomically), scans accepted current identities, resolves each event via an explicit new point lookup, and only then starts journal consumption after that captured high-water. The existing combination of separate `current`, page reads and CH page scans cannot prove an atomic bootstrap; `V1SemanticReader.read_observation(namespace,event_id,revision)` or a combined bounded bootstrap API is required from Bronze. The lookup must return verified current identity plus original canonical envelope and completed delivery lineage, read-only, and fail if absent/non-accepted/mirror mismatch. Owner: Bronze/Phase 2 interface; compatibility impact is additive. Add tests for concurrent accept/conflict during bootstrap, read-only mode, conflicted event, and incomplete CH mirror. Do not invent that API as already present.

Incremental source cursor is an exclusive durable `change_sequence`, not a CH offset. Consume ACCEPTED changes by point-reading the current identity; if now CONFLICTED, do not materialize it as accepted. Consume CONFLICTED transitions and the invalidation journal independently. Hold the fetched high-water across bounded pages. Before advancing a checkpoint, confirm source topic/namespace binding, fully reconcile all frozen CH writes and local durable obligations, and re-read source authority to ensure required status is not stale. If conflict is discovered after materialization, mark event validity false durably before acknowledging the invalidation cursor. ClickHouse invalidation mirror failures leave the intent pending; canonical Gold access consults Silver's durable validity projection and never declares the row valid from fact-table presence alone. If SQLite authority is unavailable, stop advancement and report not-ready; if CH mirror is incomplete, withhold the affected event from canonical reads and retry/reconcile. This ordering handles concurrent changes: each batch owns a bounded high-water; later sequences remain for the next batch, while an event's current-state check prevents stale acceptance.

## Run archive and evidence inventory

Producer `Visualize/runtime/run_manifest.py` writes atomically under `artifacts_root/runs/<run_id>/run_manifest.json`; its V1 fields include `simulationRunId`, `topologyDigest`, `participatingIntersectionIds`, `runGeneration`, `runStatus`, and `failedCycleCount`, alongside seed/profile/configuration/threshold/network metadata. `read_verified_v1_manifest` checks run ID, digest, exact participants, generation and READY/RUNNING status. `contracts/topology/v1_digest.py` defines projection fields and digest algorithm. Catalog-derived approaches are `catalog['approach_edges'][catalog['node_to_tls'][intersection_id]]`; no fixed direction count is justified. Current fixture direction counts A3/B3/C4/D3/M4 are only fixture assertions.

Resolver must use configured root corresponding to producer artifacts root and lookup only `<root>/runs/<simulationRunId>`. Container mount should be read-only. Verify manifest run ID/generation/digest; compute digest from archived catalog with `topology_digest`; verify participant membership and exact payload direction set; never fall back to active config. Cache verified immutable `(run_id,generation,digest)` contexts with archive file fingerprints; invalidate on changed manifest/catalog fingerprint and reject same identity with changed verified content. Missing/inaccessible path is retryable only when filesystem/transient error is classified as such; malformed JSON, mismatched identity, generation/digest, absent participant/approaches or unexpected directions are integrity failures. Historical replay resolves the historical run package, not current active topology.

## Risks / uncertainties

1. Current branch name remains the Phase 1 branch despite Phase 2 local implementation; record commit and changed paths, do not rename/switch.
2. Phase 2 final certification and its newest source changes are pending. Silver can complete the source audit and design now; implementation must verify the Bronze adapter/runtime interfaces at P3-01 entry.

4. Master Plan leaves final physical names and mapping details to Phase 3. The schema in the plan is proposed, additive, and tied only to wire/archive evidence.
5. Phase 4 must consume canonical event validity and invalidations; raw fact tables alone cannot be the serving contract because ClickHouse MergeTree inserts do not retract prior versions.
