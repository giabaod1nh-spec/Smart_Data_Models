## D3-01 — Bronze semantic authority

**Problem/options.** Current Silver reads V2 ClickHouse tables; V1 Bronze owns semantic identity in SQLite. Options: scan CH, consume the Bronze journal, or duplicate Raw classification in Silver.

**Selected.** Consume Bronze `changes` and `invalidations` from its read-only SQLite authority; use CH observation rows only through Bronze's content-verifying reader; never reclassify in Silver. Silver owns its local cursor, lock, processing state and persistence obligations.

**Tradeoffs/evidence.** SQLite becomes a runtime dependency. If unavailable, processing and canonical reads fail closed. Source: `de/bronze/checkpoint_store.py` (`V1SemanticReader`), `de/bronze/clickhouse_repository.py`, `docs/DEv1/phase-2/handover.md`.

## D3-02 — Journal-first bootstrap at sequence zero

**Problem/options.** Separate current-state scans/pages are not atomic. Considered A: snapshot accepted inventory + high-water; B: start at sequence 0 and consume retained append-only journal; C: scan CH and reconcile conflicts later.

**Selected.** B. A new Silver source binding starts at exclusive change and invalidation cursors 0, captures fixed high-waters, processes all changes through them in bounded pages, then resumes incrementally from Silver SQLite. Each ACCEPTED entry requires a current Bronze identity check and verified event point-read. If that identity is now CONFLICTED, do not emit facts; process its later conflict/invalidation entry. New sequences above the fixed high-water wait for the next pass. Startup never initializes at “latest.”

**Correctness condition.** Bronze must retain complete change/invalidation history from sequence 1 for every consumed namespace. Current `V1SemanticStore` allocates monotonically inside the state-transition transaction; `read_page` paginates without a retention boundary; no deletion/compaction API is present. Phase 2 handover calls history append-only. This is an operational no-prune guarantee, not protection from out-of-band database edits. If pruning/compaction is introduced or cursor 0 cannot be proven complete, fail closed and revisit a snapshot/export interface.

**Verification.** P3-01 validates required `v1_*` schema/fingerprint and both sequence allocators/journals in one read-only SQLite transaction. For each namespace/kind, `H=next_change|next_invalidation-1`; valid empty means no rows and H=0; valid non-empty means min=1, max=H and count=H. Otherwise fail `CURSOR_GAP`/`SOURCE_SCHEMA_UNSUPPORTED`. Bind Silver checkpoint to configured canonical DB path, namespace, expected Bronze migration/schema constants and schema fingerprint. Source does not persist a DB UUID or set SQLite `user_version`/`application_id`; identical path/schema/namespace/content replacement cannot be distinguished and is an explicit external-provenance limitation.

**Tradeoffs.** One-time catch-up can take longer than snapshot bootstrap; restarts after persisted progress are incremental. This reconstructs the *current effective state* from history, not arbitrary historical as-of state: an ACCEPTED item now CONFLICTED is suppressed. Source: `checkpoint_store.py:read_page/current`, `de/tests/bronze/test_v1_downstream_reader.py` page/restart/conflict case, Phase 2 handover.

**Impact/API.** Remove atomic bootstrap API dependency. Retain one additive point-read: `read_valid_observation(namespace,event_id,expected_revision)` returns the complete envelope and Bronze hashes only if current identity is ACCEPTED at that revision and canonical ClickHouse content reconciliation succeeds. Use existing bounded `read_delivery_lineage` separately; point-read does not promise a complete or frozen lineage snapshot. Owner Bronze. Test source state race, missing/corrupt mirror, revision mismatch and read-only mode. Existing `read_valid_observations` does not provide this point lookup.

## D3-03 — Immutable run identity, mutable lifecycle

**Problem/options.** Run configuration/topology is immutable; status changes during execution. Considered current topology, event keys alone, or archived immutable identity plus a separate lifecycle projection.

**Selected.** Resolve by run ID and archive. Immutable key `(simulationRunId,runGeneration,topologyDigest,manifest_identity)`. Reuse exact `Visualize.runtime.active_run_registry.manifest_identity`: it requires simulationRunId, topologyDigest, participatingIntersectionIds and runGeneration, and hashes all manifest fields except `runStatus` and `failedCycleCount`. Thus config/profile/threshold/PCU/asset hashes and other identity fields remain protected. Recompute `topologyDigest` from archived catalog using `contracts.topology.v1_digest`; compare digest, participant set, generation, event identity and approaches. Never use active/current topology.

**Lifecycle.** Producer writes READY manifest before run activation; registry activation sets RUNNING. `traci_runner.py` finalization selects COMPLETE when configured simulation ends successfully, INCOMPLETE after fatal runtime/structural/persistence failure, and STOPPED when interrupted or ended before configured completion. `backend.set_v1_run_status` writes failure evidence and updates registry then mirrors `runStatus` and `failedCycleCount` into manifest. Registry row is status authority; manifest status/count are mutable mirrors. Registry `INCOMPLETE` cannot later be changed to COMPLETE. COMPLETE means required captures reached durable producer SQLite, Kafka delivery may still drain. INCOMPLETE records failed cycle/runtime and `v1_failed_cycle.json`; STOPPED is an early stop without the fatal failure classification. READY is pre-publication only. Since the observation stream contains no lifecycle events, V1 Silver independently polls its known-run index every configurable 1–300 seconds (default 5), including terminal runs. Lifecycle writes compare registry availability/version/status, manifest availability/mirror/status/count/hash, and freshness. SYNCED↔LAGGING/UNAVAILABLE changes publish once; poll timestamps are local operational metadata and do not trigger ClickHouse rows. Manifest lag preserves registry status and last-confirmed count; registry outage marks registry/mirror unavailable, preserves last-confirmed state and marks stale even if the manifest remains readable. The registry `updated_at` participates only when it changes; poll timestamps remain local. Restart reloads known run IDs and refreshes them before reporting lifecycle current.

**Status eligibility.** Valid Bronze-accepted events from RUNNING, COMPLETE, INCOMPLETE and STOPPED runs remain Silver facts if event/schema/archive checks pass. READY is pre-publication and cannot authorize materialization; absent registry plus READY manifest is context only. INCOMPLETE/STOPPED set run-level partial/incomplete quality metadata; Silver does not silently delete valid observations. Phase 4 decides window eligibility/coverage. A status update never changes immutable dimension identity.

**Projection/cache.** Keep immutable run dimension fields and `manifest_identity` hash separate from `silver_run_lifecycle_v1` snapshots keyed by `(run_id,generation,registry_updated_at,status,failed_cycle_count)` with source registry/manifest hashes and observation time. Registry `updated_at` is current status time; source does not retain every lifecycle transition, so do not claim a complete transition history. Cache immutable context by run/generation/digest/manifest_identity and content fingerprints. Refresh lifecycle status independently; mutable status differences are not archive corruption. Registry identity/config mismatch is integrity failure. Registry status is authoritative if manifest status/count temporarily lags; record mirror-lag/degraded health and retry. Source: `active_run_registry.py:manifest_identity/activate/set_status/select_replay`, `backend.py` startup and `set_v1_run_status`, `traci_runner.py` finalization, `phase-3/v1-run-lifecycle.md`, `run_manifest.py:read_verified_v1_manifest` (currently validates READY/RUNNING for producer startup only).

**Tradeoffs.** Read-only archive and run registry are dependencies; absent/inaccessible sources retry, immutable mismatch faults. Legitimate status updates do not invalidate fact identities.

## D3-04 — In-place V1 runtime migration; primary lineage in facts

**Problem/options.** The approved project direction is one canonical Silver runtime. Options: refactor the existing package and service in place, retain a parallel V2/V1 runtime pair, or create a separate package tree.

**Selected.** Refactor the existing `de.silver` modules in place and keep the canonical entrypoint `python -m de.silver.main`; migrate the existing `de-silver-processor` service to V1. Do not add parallel `v1_main.py`, `v1_processor.py`, or duplicate sibling modules for responsibilities already owned by existing modules. Add distinct capability modules only where ownership is new (archive resolver, lifecycle refresher, canonical reader; a source-binding verifier only if it remains a separable capability). Update tests alongside the in-place behavior change; classify V2-specific tests as migrated, version-neutral, or retired with replacement coverage and rationale. V1 allowlists reject V2 streams. Historical V2 ClickHouse tables/data remain untouched by additive migration 008; Phase 3 performs no cleanup. Old Gold V2 must not run against V1 outputs. No separate `de/silver_v1/` tree or second Silver runtime.

**Facts/dimensions.** Add the Master Plan's direction traffic/signal and intersection grains; immutable run and topology dimensions and run/topology binding, plus separate lifecycle projection. No Camera, RunStarted or fabricated event facts. Scenario is an event field; no scenario dimension without consumer need.

**Lineage.** Each immutable logical fact freezes primary delivery `first_raw_id` plus its source topic/partition/offset and transport/source-byte hashes. No evolving-lineage snapshot is stored in canonical facts or included in fact hashes. Later identical semantic duplicates can add delivery intents without a journal change; they do not rewrite facts, invalidate the event or rematerialize logical facts. Complete current delivery history comes from bounded Bronze `read_delivery_lineage`; conflicts use Bronze invalidation provenance with original/conflicting IDs. A benign duplicate can extend that API result without changing semantic high-waters, facts, or deterministic logical hashes. Source: `checkpoint_store.py:prepare` creates SEMANTIC_DUPLICATE without allocating a change sequence; `read_delivery_lineage`; `docker-compose.yml` V2 service and `de/tests/silver` runtime/contract tests.

**Tradeoffs.** This is a controlled cutover: V2-specific transformation behavior is replaced in the one runtime after import and consumer impact is reviewed. Historical V2 data and schema objects remain. Regression coverage moves to the V1 contract and neutral helper behavior; no test is dropped without replacement coverage or explicit retirement rationale.

## D3-05 — Preserve metric value, status and presence

**Selected.** Keep numeric zero as measured zero. Required `null` carries exact `UNAVAILABLE`/`NOT_APPLICABLE` status. Absent optional metrics stay absent in canonical payload JSON and are not zero, prior value or unavailable by inference. Typed projections may be nullable; per-metric availability/presence remains recoverable. Intersection total is a separate complete-only derivation rule defined in plan.md. ## D3-06 — Authority-checked bounded read pages and invalidation protocol

**Options.** ClickHouse DELETE; ClickHouse validity mirror only; Silver SQLite validity + CH mirror with Bronze authority barrier; or rebuild only.

**Selected.** Silver SQLite owns local event state `UNSEEN → PENDING → VALID → INVALIDATED`, durable change/invalidation cursors and tombstone outbox. The Phase 3 Gold-facing contract is an in-process Python `CanonicalSilverReader`, not a new HTTP service; it owns/uses a read-only Bronze/Silver/ClickHouse session and exposes typed `CanonicalPage`/bundle results and typed exceptions with stable error codes; Phase 4 maps them at its API boundary. Facts become VALID only after Bronze current-state check and exact CH content reconciliation. `read_valid_page(query,after_key,limit,token?)` is complete-only; `query` fixes namespace/run/digest and finite `[start_seconds,end_seconds)` simulation-time scope, while `after_key` is an exclusive `(run_id,digest,event_id)` key: applied change cursor must cover captured Bronze change high-water, applied invalidation cursor must cover captured invalidation high-water, namespace/source binding must match, and each returned event must have local VALID state, current Bronze ACCEPTED identity at the observed revision and reconciled CH content. Capture authority high-waters from `v1_sequence` allocators; `read_page`'s retained boundary must equal the allocator boundary or fail `CURSOR_GAP`. Validity answers whether a returned row is trustworthy; completeness answers whether all required changes through the declared boundary were applied. No partial mode is exposed to Gold.

**Exact failure behavior.** If Silver change cursor trails authority high-water: `503 SOURCE_LAG`; if invalidation cursor trails: `503 INVALIDATION_LAG`. Bronze authority unavailable: `503 AUTHORITY_UNAVAILABLE`. Missing/stale Silver validity or incomplete/mismatched fact mirror: `503 VALIDITY_UNKNOWN`. If Bronze current status is CONFLICTED, suppress every fact for that event, commit local INVALIDATED state/outbox before acknowledging its journal cursor. Pending ClickHouse tombstone never restores visibility; retry exact frozen content. The opaque token contains the full query/time-range, namespace, both Bronze high-waters, both applied boundaries, source binding, schema/reader versions, page size/order version and exact next exclusive event key. `read_complete_scan` stages a bounded query until its final page, and on stale token discards the staged result before restarting from page one. Pagination returns entire event bundles ordered by `(simulation_run_id,topology_digest,event_id)` and counts event bundles (1–100), not fact rows; exact physical duplicates collapse and conflicting same-key content fails closed. Subsequent pages require the same token and compare both high-waters/binding at page start and end. Any advance/change discards the page and returns `409 SNAPSHOT_STALE` (binding change has its typed binding outcome). This is a bounded per-page validation barrier, not a multi-page transaction and not protection against a change committed after the final check. A stale token discards the whole accumulated scan; the caller restarts from page one with a fresh token at most three times (100/250/500 ms backoff), then raises `SOURCE_CHURN` and reports incomplete. Transient I/O retries the same page/token at most three times (four total attempts, 100/250/500 ms backoff between retries). No starvation-free progress is promised; a stable/quiescent boundary plus caught-up cursors permits completion. Typed errors are Python exceptions, not HTTP statuses; suggested mappings (lag/authority/validity 503, stale/binding 409, content conflict 500) are consumed by Phase 4.

**Gold invalidation.** Bronze invalidation carries event/run/digest/intersection/cycle/time and conflict lineage. Gold Phase 4 consumes invalidation cursor, maps event simulation time to every overlapping 60s/300s window, marks prior outputs stale/conflicted and deterministically recomputes or emits an approved revision. Existing Gold `MAX_REVISION_SEQ=1`/zero lateness must be reviewed by Phase 4. Phase 3 guarantees notification, not automatic retraction of already-published Gold rows.

**Example.** For E at R/D/B/north/cycle12, Silver facts are valid. Bronze changes E to CONFLICTED. Before Silver processes the journal, a canonical read's authority snapshot reports conflict and suppresses E despite stale Silver VALID state. Silver then persists INVALIDATED and tombstone obligation; if CH publication is pending, reads still exclude E. Gold consumes the tombstone and marks/recomputes all affected windows.

**Guarantees/limits.** Authority barrier catches conflicts committed before its snapshot; stale cursor and missing authority fail closed. A conflict after snapshot is a later change and does not retroactively alter delivered page; the next poll invalidates it and Gold must revise affected windows. No atomic transaction spans Bronze, Silver, ClickHouse, a network response and Gold. This is suitable for single-machine bounded freshness, not distributed linearizable serving. Raw fact tables are never the supported Gold read contract.

## D3-07 — Freeze obligations, primary lineage, reconcile, then checkpoint

**Selected.** Freeze exact output rows/hashes in Silver SQLite before CH writes. Fact rows carry primary lineage only. Logical hash includes semantic fact fields and verified run identity `(simulation_run_id,run_generation,topology_digest,manifest_identity)` plus immutable primary delivery coordinates/IDs/hashes; excludes evolving delivery lineage and processing timestamps. No `initial_lineage_json` field is written. Later duplicate deliveries are fetched through separate complete-lineage reader and do not alter fact content or replay equivalence. Reconcile every fact/dimension/validity/tombstone after uncertain write; finalize local state only after exact obligations exist; advance each source CAS cursor only after durable local state and required frozen publication obligations are complete. Conflict provenance retains both relevant deliveries.

**Tradeoffs/evidence.** CH reads and SQLite metadata increase. Crash recovery is deterministic; content mismatch faults closed. Reuse `SilverCheckpointStore` CAS/SQLite WAL patterns after changing V2 offset semantics; `V1SemanticReader.read_delivery_lineage` proves separate lineage access.

## D3-08 — Replay requires a stable verified source boundary

**Selected.** Replay manifest freezes source namespace/binding, change/invalidation high-waters, run ID/generation/digest/manifest identity, replay ID, reader/processor/schema versions and archive fingerprints. Replay represents current effective state at that verified boundary; it is not arbitrary historical as-of. At start, resume, each bounded batch and completion, require current allocators to equal the frozen high-waters and complete-history verification to pass. Any advance returns `SOURCE_BOUNDARY_CHANGED`, aborts and makes the replay ID non-resumable; issue a new manifest. Replay cannot run while Bronze is actively receiving changes. Separate replay SQLite/checkpoints/IDs/locks and ClickHouse targets; never mutate live. Incomplete replay is not a successful reconstruction.

**Evidence/tradeoff.** Bronze `current()` is current-state, not time travel; journal is append-only. Stability checks make same-manifest repeat deterministic only while source remains at the frozen boundary. No historical snapshot subsystem is added.

## D3-10 — Phase 4 in-place Gold V1 cutover and window policy

**Selected.** Phase 3 exits with working Silver V1 fact/dimension tables, durable validity/invalidation feed, tested complete-only Python reader/token/error interface, mappings and acceptance evidence. Phase 4 refactors existing `de/gold/` and `de/gold_runtime/` in place into one Gold V1 implementation/runtime. Gold V1 consumes the canonical reader and invalidation feed, never raw fact tables. It owns nullable analytics, archived-topology direction mapping, window freshness/revision, lifecycle quality and correct run/scenario selection. The current Gold V2 `SilverReader` allowlists V2 table names; current inputs require numeric wait/arrival values and context builder defaults waiting to zero. Do not redirect it to V1 tables.

**Tradeoffs.** Historical Gold V2 data remains preserved; an executable V2 Gold process is not required during cutover and must not read V1. Spring Gold repository SQL, DTO/mapper null handling, run/scenario selection, and Dashboard compatibility remain later acceptance. Phase 3 does not implement Gold, Spring or Dashboard and does not claim compatibility.
