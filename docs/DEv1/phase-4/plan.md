## Target runtime and ownership

```text
Bronze V1 journals and current semantic identity (Silver's upstream authority)
                              │ Silver only
                              ▼
Silver V1 public canonical change feed + independent invalidation feed
                              │ bounded page + JCS/SHA-256 receipt
                              ▼
Existing Gold adapter/coordinator (refactored in place)
                              │ Gold-local SQLite transactions
                              ▼
Source binding/cursors · receipts/transitions · suppression · event/window membership
work intents · dirty generations/recompute · retries/faults · replay manifest
                              │
Foundation health/metrics only — no business marts or result publication
```

Gold calls only `discover_canonical_source`, `read_canonical_changes_page` and `read_canonical_invalidations_page` through the public Silver API. It does not open Bronze or query Silver physical facts. Silver may read its internal repositories/ClickHouse facts to construct and reconcile canonical bundles. Never derive progress from event ID, CH insertion time/row counts, private Silver methods or decoded legacy tokens.

Production progress verifies the entire normative receipt: contract version, namespace, binding, requested exclusive cursor, actual returned interval, exact contiguous coverage, count, complete-envelope encoded bytes, JCS/SHA-256 digest and receipt ID, captured Bronze/Silver boundaries and safe invalidation watermark. A saved cursor advances only to actual `through_sequence`, in the same Gold SQLite transaction that durably records each immutable transition and all required membership, suppression and work obligations. The receipt is not a distributed snapshot. Appends above captured high-water are deferred; they do not invalidate a safe page. `has_more=false` means no more sequence exists in that response's captured eligible prefix only.

Change and invalidation cursors are independent. Before acknowledging a change receipt Gold consumes invalidations through its fixed safe `Pi=min(Hi,Si)`, not a continuously moving `Hi`. A pending CH invalidation mirror does not permit ignoring Silver's durable local invalidation. For changes, `Pc=min(Hc,Sc)`; Silver truncates at the first unsafe effective disposition. Do not require Silver to catch live Bronze. Gold treats `BUNDLE_VALID`, `SUPERSEDED_BY_CONFLICT` and `CONFLICTED` distinctly. Preserve immutable `source_transition_hash`, historical receipt, effective disposition and `bundle_hash`; a changed effective disposition at a later boundary is a correction, while an immutable transition hash change for a committed sequence/binding fails closed.

Cold bootstrap verifies retained history once for a new source binding, then Gold initializes both cursors at zero. Same-binding resume validates binding, cursor range and next-prefix continuity; it does not repeat the full scan. Source replacement, rewind, unsupported schema or retention gap stops with no cursor reset. Run discovery covers journaled runs only; representing empty runs requires an additional approved registration source. Existing `read_complete_scan()` is fixture, compatibility and bounded smoke use only.

## Gold V1 durable state contract

Use Gold-owned SQLite at `de/artifacts/gold_v1/checkpoint.sqlite3` and `de/artifacts/gold_v1/instance.lock`. Preserve all V2 state under `de/artifacts/gold/`. Exactly one process owns the active namespace. Additive migrations must be versioned, idempotent and transactional; they must never silently adopt V2 cursors/schema or remove V2 data. No full copy of Silver facts in Gold SQLite and no ClickHouse Gold migration unless a concrete need is separately approved.

Logical entities and required keys/invariants:

| Entity | Key, constraints and indexes |
|---|---|
| Source binding | Namespace + binding ID + contract/source/schema/reader versions; immutable once used by a cursor. One active binding per live namespace. Replacement requires explicit new bootstrap generation. |
| Feed cursor | `(namespace, feed_kind)` unique; feed kind CHANGE/INVALIDATION; exclusive sequence, binding, CAS generation. Independent rows. |
| Page receipt / transition | One bound authority per store. Retain immutable receipt headers and sequence/disposition/provenance, transition hashes and bundle hashes. Verify complete canonical page bytes before acknowledgment. Complete historical page bytes are kept only for selected disposable acceptance fixtures. A persisted digest cannot reconstruct historical payloads. See the [implementation contract](implementation-status.md#final-review-decisions). |
| Event identity/suppression | Unique source binding + event identity; source hash/revision, pinned run identity, current effective status, suppression reason and source invalidation sequence. Suppression exists without a window row. |
| Window candidate/state | Unique versioned full generic window identity. Independent eligibility, source boundary, completeness, processing, dirty generation, finality and run lifecycle fields. Index state/eligible time. `UNKNOWN` completeness and `DISABLED` finality in Core. |
| Membership | Unique `(event_identity, window_identity)` with simulation-time coordinates/scenario provenance; indexed by event for invalidation impact. At most one membership per duration for an event/window specification. |
| Work/recompute | Unique window/generation work row and deterministic completed work ID from processing namespace, window, generation, input hash and versions. Keep immutable completed work. Recompute streams indexed members by exact source sequence through the public API and checks transition/bundle hashes, invalidation boundary and local generation. |
| Replay | Deterministic replay ID and frozen manifest/hash/binding/boundary/scope/versions; separate SQLite database, lock and namespace; never shares live cursors or work. |
| Migration/lease | Versioned migration table; one namespace lease/owner generation. Never run two active owners. |

Use indexed lookups for sequence continuation, event identity, invalidation-to-membership, ready work and recovery. Gold transactions use explicit `BEGIN IMMEDIATE`/commit/rollback and cursor CAS. A successful change page transaction stores verified receipt and immutable transitions, materializes eligible bundle identity/membership, enforces suppression, records work obligations and advances change cursor atomically. A successful invalidation transaction stores receipt, suppression, every indexed impacted membership/window, increments dirty generation, creates recompute obligations and advances invalidation cursor atomically. Change ack is forbidden until required invalidations through its fixed Pi are committed. If an invalidation arrives while change work is preparing, check suppression/generation inside the final transaction; either create a dirty intent that includes the newer generation or abort/retry. Crash before commit leaves all cursor/state unchanged; after commit all obligations/cursor recover together.

No transaction spans Silver, Bronze, Gold SQLite or ClickHouse. A conflict after Silver's final validation may arrive after Gold stores a valid earlier-boundary receipt; the later invalidation converges Gold state. This is Gold-local atomicity and eventual convergence, not distributed transaction or snapshot isolation. Nothing in Core is serving-safe business output.

## Work windows and backlog-aware runtime

Use pure Tumbling Windows in simulation time: exactly 60s and 300s, deterministic `[start,end)`, epoch-zero alignment preferred. Finalize time precision/normalization and run-boundary behavior before durable identities. Each event maps once per configured duration. Generic window identity is exactly namespace, run ID, generation, topology digest, manifest identity, window-spec version, duration and endpoints. Bind source schema and processor versions to the relevant processing identity, input-set hash and work identity. Keep scenario per event/input hash; exclude it from generic window identity. Preserve run lifecycle independently. Never assume fixed IDs, directions, cadence or sample count.

Core continuously consumes observations and records durable work/membership even while a window is open; do not wait until end. Candidate scheduling is independent of completeness/publication. `window_completeness=UNKNOWN` until Phase 4B approves expected observations/coverage; `publication_finality=DISABLED` and `FINALIZED` unreachable. A passed end or COMPLETE simulation run proves neither completeness nor finality. No rolling/sliding windows or provisional aggregation/results.

Runtime scheduling loops immediately while safe bounded work remains, with fairness among change pages, invalidation pages and window work. Choose a bounded interleave/reservation and test starvation prevention; invalidation-before-change remains mandatory. When no processable work remains, use idle polling. Dependency/source errors use bounded exponential retry/backoff; blocked prefixes must not busy-loop. Respect entry/page bytes, page deadlines, transaction duration, bounded in-flight work/stage, RSS and disk limits. Graceful shutdown stops intake, finishes or rolls back the current local transaction, retains cursors and releases the lease. Do not assume a larger page or worker count increases throughput. The legacy two-second poll and one-window-per-cycle are not optimality decisions.

Mandatory measurements: actual source observations/s and bytes/s; simulation-time vs wall-clock progression; Outbox pending rows/bytes/oldest age; Kafka lag; Raw persistence; Bronze semantic progress; Silver change/invalidation applied sequence and lag; Gold change/invalidation acknowledged sequence; pending/dirty work; backlog size, age and growth per stage; source-to-Gold durable-work latency; Silver-to-Gold feed and transaction latency; window candidate delay; batch/page duration; p50/p95/p99/max latency; CPU, peak RSS, SQLite DB/WAL growth and transaction cost, ClickHouse query count/latency/resource pressure, retry/timeout/blocked-prefix/fault counts, catch-up/recovery duration, free disk and retention headroom. Never equate row counts across layers; join by source identity and sequence with independent correctness oracles. Distinguish retained data growth, unprocessed observations, invalidation backlog, pending work and publication delay.

## Recovery and replay

On startup: acquire the single-owner lease; verify runtime schema and binding; recover/abandon partial local stages only if a measured, bounded staging design is actually required; resume independent invalidation from its committed cursor; consume invalidations through the fixed Pi before change ack; read change page from durable exclusive cursor; verify receipt and exact sequence; atomically record obligations and CAS. On crash before either feed transaction, replay from its old cursor. After commit, cursor and all obligations resume together. Duplicate delivery is idempotent. Receipt verification failure leaves cursor unchanged. Changed binding, retention gap, immutable hash mutation or unsupported version fails closed without reset.

Replay freezes an applied source boundary, binding, run/generation/topology/manifest identity, contract/schema/processor versions and scope. Gold replay reads Silver namespace `live` and writes to its own processing namespace, SQLite DB and lock. An active replay ID aborts on a changed boundary. Transient outages remain retryable. Replay supports current effective state at the verified boundary.

## Benchmark and performance boundary

The retained Pre focused benchmark used genuine replayed V1 observations through Bronze/Silver and the Silver feed with a test-only SQLite consumer: 150 entries applied/acknowledged over 600s (0.25/s); 255 sequences/bundles, 221 receipts, 5,255,148 encoded bytes; controlled 30-entry backlog after a two-minute consumer pause drained in 28.23s; page read plus test acknowledgment p50/p95/p99 828.1/949.0/1,152.3ms. It used a paced cycle every 20 wall seconds. A five-second trial failed to achieve its offered cadence because replay/apply took about 14–15s per five-observation cycle. This was not the full live pipeline and did not measure actual Gold, Kafka or Raw; the pause was not a true producer burst. These are a tested workload, not maximum sustainable capacity.

After Stage B correctness, perform an end-to-end benchmark based on scenarios A–H in [`pre/capacity-and-backpressure.md`](pre/capacity-and-backpressure.md): normal; accelerated; sustained; true producer burst/catch-up; dependency outage/recovery; continuous conflict/invalidation; bootstrap/restart; constrained hardware. For five intersections with one full cycle per wall-second, five observations/s is a representative assumption to verify from actual producer behavior, not a universal cadence. Record actual producer rate, resource limits, duration, data volume and owner-approved objectives. No 10-second latency SLO is approved. Do not pause/reduce the producer, drop data, skip reconciliation, or expand Core into an upstream rewrite to manufacture PASS. If capacity fails, profile the measured bottleneck and create a separate before/after performance-remediation plan.

Acceptance verdicts remain separate: correctness `PASS/FAIL`; capacity `SUSTAINABLE AT TESTED WORKLOAD / BURST RECOVERY VERIFIED / CAPACITY INSUFFICIENT / INCONCLUSIVE / NOT MEASURED`; operational readiness `PASS/FAIL`. Core makes no Gold-to-Dashboard latency claim.
