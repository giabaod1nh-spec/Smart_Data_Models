Keep valid semantic requirements from the Master Plan, including nullable values and late-data correctness; do not carry forward conflicting runtime strategy. ## Upstream Silver V1 contract and risks

`de/silver/canonical_reader.py` exposes `CanonicalSilverReader`, `CanonicalReadSession`, `CanonicalReadQuery`, `CanonicalPage`, `ObservationBundle`, `read_valid_page`, `read_complete_scan`, and `read_invalidation_page`. Pages are complete event bundles, ordered by exclusive `(run_id, topology_digest, event_id)`, limited to 1–100 bundles. Token claims bind query, page size, binding, reader/schema/order versions, both Bronze high-waters and both applied Silver cursors. The token is Base64 JSON, not authenticated; it is not an authorization credential. It is acceptable only as an in-process continuity token when Gold treats it as opaque and the reader validates all claims. Do not accept client-supplied tokens across a trust boundary. Malformed/mismatched tokens fail `SNAPSHOT_STALE`.

Reader errors carry stable `code` and `retryable`: source/invalidation lag, authority unavailable, validity unknown, snapshot stale and source churn are retryable; binding changed and canonical content conflict are not. `read_valid_page` fails without partial bundles, applies start/end source-boundary checks, and rereads current validity; `read_complete_scan` stages pages, retries transient reads at most four times, restarts stale scans at most four total attempts, then raises `SOURCE_CHURN`. The interface has no HTTP status behavior. Reader sessions own connections; ClickHouse clients must have SELECT-only grants. Page `complete=True` is page-scoped, not a cross-page snapshot guarantee.

`read_invalidation_page(after_sequence, limit<=100, source_binding)` is independent, global sequence order, requires persisted binding on resume, returns pending mirror count, and is not a complete-fact-scan certificate. Persist its sequence and source binding together. Consume invalidations even when their CH mirror is pending; Silver SQLite validity is authoritative.

**Incremental gap (blocking design decision for production polling):** the canonical interface does not expose a change-sequence feed for valid observations, a run enumerator, or a continuation cursor on `read_complete_scan`. Query requires run/digest and complete scan returns bundles only. Thus Gold cannot safely discover all new accepted events by polling a saved event ID, ClickHouse insert time, or row count. Hashed event IDs are not an event-time watermark; late events can sort before a saved key. The invalidation feed solves suppression only. Recommended: approve a Silver-owned canonical incremental API that emits complete bundles keyed to frozen change high-water/source binding and independently gates invalidations/applied cursors; retain canonical point validity checks and whole-page/batch stale discard. Until such an API is delivered, a bounded full canonical rescan with Gold-side identity/hash dedupe is correct but has O(retained observations) polling cost; it is acceptable only for measured bounded fixtures or an explicit throughput gate, not presumed production scalability. This is an owner decision/dependency, not an invented existing API.

Lifecycle has separate registry and archive availability paths. `LifecycleRefresher.poll` can retain registry status while archive is unavailable and mark manifest mirror unavailable; registry outage preserves prior confirmed status. `failure_evidence_json` is nullable in migration 008; producer code has a failure artifact path (`v1_failed_cycle.json`) but Phase 3 report does not prove universal population. Gold should model registry current, archive unavailable, lifecycle stale, and source completeness separately; never infer failure evidence from null. These are resilience states, not proof that observations are incomplete.

## Producer and migration facts

`contracts/traffic_observation.py` builds V1 event envelopes with `simulationTimeSeconds`, `cycleSequence`, `scenario`, `simulationRunId`, `topologyDigest`, `eventId`, capture time and producer provenance. Event identity derives from schema version, run ID, intersection ID and cycle sequence. Contract declares values/presence; it does not establish one fixed cadence or four directions. `Visualize/runtime/run_manifest.py` carries `topologyDigest`, `participatingIntersectionIds`, `runGeneration` and `runStatus`; `active_run_registry.py` defines immutable `manifest_identity` excluding mutable status/failed-cycle fields and stores lifecycle status separately. Archived topology/digest and each run generation must remain distinct. Run states include READY/RUNNING/COMPLETE/INCOMPLETE/STOPPED; READY is pre-publication, terminal status does not itself prove every window complete.

Migration 005 contains business marts and serving views; migration 008 is additive Silver V1 and its 20-table schema is upstream only. Do not edit either migration. Gold's current SQLite `GoldRuntimeStore` already contains checkpoint/window/work-unit/lease/migration state and CAS support, making it the preferred foundation state owner. A Gold ClickHouse infrastructure migration is not yet justified: prefer SQLite for coordination and no Gold analytics output in 4A. If an approved later need requires CH durable shared state, add a separate additive migration after schema review and V2 sentinel verification.

## Audit conclusion

The repository has substantial reusable Gold orchestration, CAS, locking, metrics, replay isolation and pure window/quality code, but the active source adapter and calculation/output path are incompatible with V1. The approved in-place cutover can preserve these infrastructure patterns while replacing V2 source identity, validity, revision and output semantics. The main unresolved technical dependency is efficient canonical incremental discovery; finality/lateness policy is a separate explicit approval decision. No runtime or application code was changed by this audit.
